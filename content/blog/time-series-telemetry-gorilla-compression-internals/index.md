Operating large-scale telemetry systems requires processing and storing billions of data points per second. Each data point fundamentally consists of a timestamp and a numeric measurement, typically represented as a sixty-four-bit integer and a sixty-four-bit double-precision floating-point value. Storing these sixteen-byte samples raw quickly exhausts memory bandwidth, network capacity, and disk space. To mitigate these constraints, modern time-series databases and performance monitoring engines rely on highly specialized, bit-level compression algorithms. The gold standard for this is the Gorilla compression format, which achieves remarkable compression ratios by exploiting the mathematical predictability of telemetry streams.

Traditional compression utilities such as Gzip or ZSTD are designed for general-purpose byte blocks. They operate over sliding windows to find repeating patterns, making them far too computationally expensive for real-time write pipelines. Telemetry demands algorithms that can compress and decompress streams on the fly with single-digit nanosecond latencies. Gorilla achieves this by evaluating timestamps and floating-point values independently, applying distinct bit-packing heuristics optimized for the mathematical characteristics of each data type.

The timestamp compression mechanism relies on a predictive model called double-delta encoding. Assuming metrics are collected at uniform intervals, the difference between consecutive intervals should theoretically be zero. Given three consecutive timestamps, the first delta is calculated by subtracting the first timestamp from the second. The second delta is calculated by subtracting the second timestamp from the third. The double-delta is then computed as the difference between these two deltas. If this double-delta is zero, the engine stores a single zero bit. If the double-delta falls within a small range, the engine prefixes the value with a two-bit control header of one-zero and appends seven bits of data. For wider variations, a three-bit control header of one-one-zero is prefixed followed by nine bits of data. If the variation is even larger, a four-bit header of one-one-one-zero precedes twelve bits of data. In extreme cases of out-of-band anomalies, a four-bit header of one-one-one-one is written followed by the entire thirty-two-bit raw delta.

This variable-length bit-packing scheme is highly effective because telemetry agents typically push metrics at fixed schedules. A metric configured to run every ten seconds will occasionally experience minor jitter due to network latency or CPU scheduling. The double-delta for an eleven-second interval following a ten-second interval is exactly one second. Instead of writing a full sixty-four-bit timestamp, the compressor writes a short bit sequence containing only the delta variation. When the sampling interval is perfectly consistent, a sequence of hundreds of timestamps can be compressed down to just one bit per sample.

Compressing the floating-point values requires a radically different strategy. To understand why simple delta encoding fails for floating-point values, we must examine the IEEE seven-fifty-four specification. A double-precision float is split into one sign bit, eleven exponent bits, and fifty-two fraction bits. Because fractional values shift physical bit boundaries drastically even with small scalar variations, subtracting two floats often produces a value that still requires a full sixty-four bits to represent. XORing adjacent values bypasses this mathematical limitation. Because consecutive telemetry measurements usually share identical high-order bits for the sign and exponent, and often share a substantial portion of the mantissa, the XOR operation yields a bit-pattern saturated with leading and trailing zeros.

To compress the floating-point values, the algorithm first computes the XOR of the current value with the previous value. If the resulting XOR value is zero, it indicates that the metric has not changed, and the engine writes a single zero bit to the stream. When the XOR value is non-zero, a one bit is written, and the algorithm evaluates whether the position of leading and trailing zeros matches the previous data point's pattern. If the block of meaningful bits fits within the previous boundaries, the engine writes a zero control bit followed by only the meaningful bits. If the boundaries have changed, it writes a one control bit, followed by five bits representing the number of leading zeros, six bits representing the length of the meaningful block, and finally the actual meaningful bits.

Consider a metric measuring CPU utilization. If the CPU utilization sits at seventy-five point zero percent for consecutive readings, the XOR result is zero, requiring a single bit. If it fluctuates slightly to seventy-five point one percent, the sign and exponent bits remain identical. The XOR operation zeroes out those identical high-order bits, leaving only a small set of changing bits in the mantissa. Instead of storing sixty-four bits, the engine dynamically adjusts its window to store only the shifted mantissa bits, skipping all leading and trailing zeros. By maintaining state about the previous XOR block's leading zero count and meaningful bit length, the engine avoids rewriting metadata for steady-state oscillations.

From a memory hierarchy perspective, the design of these codecs is exceptionally friendly to modern hardware. The algorithms perform no dynamic memory allocations and avoid branch-heavy loops, making them highly predictable for CPU branch predictors. Because decompression is a pure forward-scanning bitstream read, it can be implemented with efficient bitwise shifts and masks. This enables query engines to scan millions of compressed points per core-millisecond. The stream can be decompressed on the fly directly in the L1 or L2 CPU cache, bypassing the main memory bus bottleneck that typically limits large-scale analytical query execution.

This format does present engineering tradeoffs. Because both timestamp and floating-point values are packed as a continuous bitstream rather than aligned bytes, random access within a compressed block is impossible. To read the thousandth data point in a block, the query engine must sequentially decompress the preceding nine hundred and ninety-nine points to reconstruct the rolling state. To minimize this decompression overhead, time-series databases segment data into bounded blocks, typically covering two-hour or four-hour windows. Each block starts with a raw, uncompressed timestamp and value keyframe. This layout bounds the maximum number of decompression steps required to resolve any individual point while keeping the average compression ratio extremely high.

Engineers implementing this pattern in high-throughput pipelines must pay careful attention to bit-endianness and CPU cache line alignment. When writing variable-length bits to a byte-oriented buffer, buffering bits in a sixty-four-bit register before flushing them to memory prevents the pipeline from stalling on sub-byte writes. Modern implementations in systems such as Prometheus, ClickHouse, and custom telemetry processors demonstrate that Gorilla-style compression consistently reduces the memory footprint of active metrics by over eighty-five percent. Implementing these low-level bit manipulation techniques directly impacts both operational storage costs and query latency at scale.
